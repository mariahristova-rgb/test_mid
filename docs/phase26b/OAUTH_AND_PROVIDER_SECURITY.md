# Customer OAuth security and operator configuration
Default is disabled. Set ASSISTANT_CUSTOMER_OAUTH_ENABLED=true only in a reviewed environment, with ASSISTANT_CUSTOMER_OAUTH_APPLICATIONS JSON containing PlatformOAuthApplication records (provider, client_id, secret_reference, exact HTTPS redirect_uri and allowed_redirects). Secrets are server-managed ASSISTANT_CUSTOMER_<PROVIDER>_CLIENT_SECRET using the existing deployment_secret loader. Customers never supply client credentials. Outlook additionally requires ASSISTANT_CUSTOMER_OUTLOOK_TENANTS. Do not copy owner credentials/tokens into customer connections.

Fixed provider HTTPS egress, bounded timeout/response size, no redirects and no caller TLS/transport override. Google/Microsoft validate signed identity; Calendly authenticated identity and HubSpot client-bound introspection. Refresh verifies the same account and rejects scope downgrades. OAuth state, cookie binding, tenant/user/provider, expiry, nonce, revision and application fingerprint are checked; denial also consumes validated state. Callback redirects to a clean integrations URL without codes/tokens.

Encrypted account/token/resource mappings remain server-side; production resource references are opaque. Disconnect revokes local vault records and denies subsequent writes. Provider-side grant revocation is not asserted. Existing owner integration and fixture routes remain separate compatibility paths. Server live-write switch ASSISTANT_CUSTOMER_CALENDAR_WRITES_APPROVED is independently required and has not been enabled.

Synthetic negative tests cover replay, tenant mixup, forged identity, issuer/audience/nonce, refresh account changes, scope downgrade, disconnect races, resource selection and outbound URL restrictions. Multi-instance PostgreSQL runtime is not accepted; SQLite transaction claims alone do not establish distributed production readiness.
