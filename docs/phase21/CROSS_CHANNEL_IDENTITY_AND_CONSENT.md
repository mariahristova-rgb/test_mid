# Continuity contract proposed for separate review

NOT IMPLEMENTED/AUTHORIZED. Current operator contact_links/evidence is not a customer verification proof. Matching names,email strings or phone text must never disclose another session's context. No raw history is duplicated. This proposal reviews new contracts before any runtime/API implementation.

## Prototype scope and persistence

First local prototype uses existing operations_events/contact references and strict purpose-scoped proof service; schema5unchanged. Default external proof delivery unavailable; only a server-controlled synthetic test transport permitted in explicit development fixtures. Production must fail closed when the approved proof transport is absent; no client flag can select mock verification. No real email/phone/SIP/Google action or identity migration.

## Proposed widget contract

Proposed persistence review (existing operations_events only): continuity_challenge stores purpose,session/conversation refs,subject HMAC,code HMAC,consent,attempt count,status,expiry; continuity_proof stores consumed challenge ref,verified subject HMAC,current session binding,status,expiry; continuity_offer stores verified source proof/ref,neutral booking revision/context scope,explicit consent,status,expiry; continuity_resume stores offer/destination proof refs,event fingerprint,status/correlation; revocation changes offer/proof status and invalidates unfinished resume authority. Every record has server-derived tenant ID; no plaintext OTP,address,raw transcript,phone recording or independent customer profile. Optional existing contact refs are authorized server-derived links,never a new customer table or upgrade of operator evidence. Erasure withdraws the offer and redacts projection data without deleting committed appointments. These new JSON kinds/purposes need owner design review before code.

All paths remain behind existing widget Origin/nonce/session policy; tenant,source conversation and current visitor are derived from the authenticated capability,never body fields.

1. POST `/widget/continuity-challenge/{public_id}` body `{purpose:"offer"|"resume",identity_kind:"email",address:string,consent:true}`. StrictBoolean consent; purpose/language scoped. Returns opaque challenge_id,queued_mock/blocked status,expiry≤600s. No subject existence/history disclosure. Phone flow BLOCKED until a separately approved server verification method exists.
2. POST `/widget/continuity-confirm/{public_id}` body `{challenge_id:string,code:string}`. Limited attempts≤5,expiry,single use,tenant/session/purpose/nonce binding. Code stored only keyed hash; verified subject HMAC is server-derived from successful transport proof,never client supplied. Returns proof receipt only,not transcript or staff authority.
3. POST `/widget/continuity-context/{public_id}` body `{proof_id:string}`. Requires a verified resume proof plus previously verified source offer with explicit consent for the same subject/tenant. Returns neutral unfinished booking summary (date/duration/service/reference/timezone/locale) only; no names/raw chat/audio/approval ID/management token. Unknown or unlinked subject gets generic unavailable response.
4. POST `/widget/continuity-continue/{public_id}` body `{proof_id:string,offer_id:string,confirmed:true,event_id:string}`. Recheck proof/consent/revocation and source revision/status; accept context into current authorized session only. Recheck availability and request a new consequential-action confirmation through existing booking tools; never copy or approve old pending approval. Does not itself book/send.
5. POST `/widget/continuity-revoke/{public_id}` body `{offer_id:string,confirmed:true}`. Only source/destination authorized proof owner; idempotent revocation prevents future context reads/continues. Existing committed booking and financial records unchanged; pending resume authorization invalidated.

These are proposed additive public contracts,not existing routes. Bounds for review:address≤250characters;opaque challenge/proof/offer IDs≤100;code exactly6digits;event_id1–80characters[A-Za-z0-9_-];consent/confirmed strict booleans that must be true;unknown fields rejected. Challenge/proof TTL≤600seconds;source offer retention≤min(7days,tenant policy);max5code attempts,max5active challenges per session. Use existing localized DomainError/error envelope for invalid_input,verification_required,ownership_required,expired,disabled,conflict and rate-limit refusal; no sensitive assertion/payload in response.

Outputs for review: challenge_id/status/expires_in; confirmation proof_id/status/expires_in; context offer_id/status/locale/timezone/neutral_booking_context; continue status/context_applied/confirmation_required/duplicate; revoke revoked/duplicate. Test-only delivery is internal injected transport; never return plaintext OTP or let an API field choose mock verification. With no approved transport,all proof operations fail closed as unconfigured. No token returned in parent postMessage,URL query or logs.

Voice uses an internal hook bound to existing authenticated voice ticket/call/tenant; a phone/callerID alone is not proof. Destination customer must independently verify the same subject and explicitly accept continuation. Email follow-up needs separate send consent/recipient authorization. Mobile is same verified web capability flow,not an automatic shared-storage identity.

## Invariants and tests

Source consent alone does not authenticate destination. Destination email proof alone does not authorize histories lacking source offer. Forbid cross-tenant/source-ID enumeration,replayed/expired challenges,client verified flags,forged proof,wrong purpose/session,revoked links and leaked tokens. Store minimal retention≤tenant policy,erase/revoke after chat privacy cleanup,never auto-merge contacts from strings. Operators see categorical IDs/status only,not unapproved history.

Race tests: source booking changes before resume,concurrent destination sessions,revocation before execution,completed/unknown writes,expired pending approval and reconnect replay. Existing transaction/intent/calendar guards remain authoritative; single-process lock is not distributed HA. Separate fake proof fixtures from real ownership delivery evidence. Public production use remains BLOCKED until transport and security/browser acceptance are approved and verified.
